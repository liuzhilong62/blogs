同事 Umair Shahid（Stormatics）最近写了一篇生产事故复盘，一个 11TB 表的逻辑复制迁移，因为初始 COPY 持有 snapshot 太久，触发了三级连锁反应。我来拆一下。

## 问题现象

场景：生产 OLTP 库，最大的一张 append-only 表约 11TB。同一个库里跑着一个 job queue，用 `SELECT FOR UPDATE SKIP LOCKED` 处理任务。准备通过逻辑复制迁移到新版 PG，初始数据同步用 COPY。

流程看起来合理：先同步最大的表，给监控和调整留足时间。staging 环境跑过多轮演练，COPY 顺利完成，资源消耗在预期范围内，一切都绿。

然后上了生产。COPY 跑了几个小时。第二天早上，库 CPU 100%（24 核全满），job queue 积压 700 万行，客户开始投诉延迟。

staging 演练全绿，生产炸了。为什么？

## 第一级：Bloat 爆炸

问题起点很经典：**长事务**。

COPY 在运行期间持有一个事务快照（snapshot）。PG 的 autovacuum 有一个铁律：**不能清理任何比集群中最老快照还新的 dead tuple**。这个规则作用于集群里的所有表，不只是正在 COPY 的那张。

job queue 表本身就是高频写入——每处理一条任务就标记一个 tuple 为 dead。在生产写入速度下，dead tuple 以百万级别堆积。autovacuum 的清理边界被 COPY 的快照锚死了，眼睁睁看着 bloat 膨胀。

```sql
-- 直观感受：job queue 表在长事务期间的膨胀
SELECT schemaname, relname,
       n_dead_tup,
       n_live_tup,
       round(n_dead_tup * 100.0 / NULLIF(n_live_tup + n_dead_tup, 0), 1) AS dead_pct
FROM pg_stat_user_tables
WHERE relname LIKE '%queue%'
ORDER BY n_dead_tup DESC;
```

当 active queue 表的 dead tuple 超过 400 万时，`SELECT FOR UPDATE SKIP LOCKED` 的查询延迟突破了 1 秒。index scan 在不断增加无效 heap pointer 的情况下越来越慢。

这还没完——处理变慢意味着队列写入速度超过了消费速度，积压呈指数增长。DBA 第二天早上发现时 CPU 已经打满，立即杀掉 COPY，手动 VACUUM。吞吐恢复。

## 第二级：SLRU 争用

消停了大概 30 分钟，吞吐又开始掉。

这次瓶颈不在 bloat，在 **multi-transaction SLRU**。

`SELECT FOR UPDATE SKIP LOCKED` 有一个不容易注意到的副作用：当多个并发 worker 同时扫描同一段索引热页时，它们会争抢 multi-xact 缓冲区。轻量级锁等待（lightweight lock waits）在等待事件里占了主导。

```sql
-- 发现 SLRU 争用的典型等待事件
SELECT wait_event_type, wait_event, count(*)
FROM pg_stat_activity
WHERE state = 'active'
GROUP BY 1, 2
ORDER BY 3 DESC;
-- 看到大量 LWLock / MultiXact*
```

第一反应是继续 VACUUM——没用，瓶颈已经从存储层移到了更底层的并发控制。

解决方式：**把索引扫描的起始位置随机化**。原来所有 worker 都从索引头部开始扫，等于在排队抢同一组 page。改成随机位置后 worker 分布在 keyspace 不同区域，multi-xact 争用消失。

```sql
-- 改造前：所有 worker 从索引头部开始
-- SELECT ... FROM queue WHERE status = 'pending'
-- ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 10;

-- 改造后：随机起始位置
-- SELECT ... FROM queue WHERE status = 'pending' AND id > random_start()
-- ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 10;
```

## 第三级：Transaction Wraparound 逼近

几个小时后又一个告警：集群事务号冲到了 1.95 亿。

这个其实不是紧急情况。PG 的 `autovacuum_freeze_max_age` 默认在 ~2 亿附近触发预防性 freezing，这是系统正常行为。真正危险的阈值在 10 亿附近。

```sql
-- 检查事务回卷距离
SELECT datname, age(datfrozenxid) AS xid_age,
       round(age(datfrozenxid) * 100.0 / 2000000000, 2) AS pct_to_wraparound
FROM pg_database
ORDER BY age(datfrozenxid) DESC;
```

但调查中又发现了一个隐藏问题：之前在事故中有一个 Patroni 备库掉队，后来从另一个 standby 重建了。重建时留下的 **旧 replication slot 没有被清理**，它持有一个 `backend_xmin`，继续锚定 vacuum 清理边界——即使 COPY 早就被杀了。

```sql
-- 发现残留 replication slot
SELECT slot_name, slot_type, database,
       active, xmin, catalog_xmin
FROM pg_replication_slots
WHERE NOT active;
```

删掉这个 slot 后，vacuum 边界释放，集群彻底稳定。

## 为什么 staging 没测出来

这一点最值得反思。

staging 的演练流程是：跑 COPY → 复制追上 → 资源消耗正常 → 通过。每次演练都绿。

问题在于 staging 没有模拟生产环境的**并发写入负载**。COPY 跑的同时没有 job queue 在跑——没有 dead tuple 产生，没有 bloat，没有 SLRU 争用，更没有 replication slot 残留。演练验证的是 COPY 本身能不能跑完，但真正的风险是 COPY 对其他负载的**副作用**。

## 总结

这次事故的根因是长事务，但它暴露了三个层层递进的瓶颈：

| 级别 | 症状 | 根因 | 修复 |
|------|------|------|------|
| L1 bloat | job queue 延迟飙到秒级，700 万积压 | snapshot 锚定 autovacuum | 杀 COPY + 手动 VACUUM |
| L2 SLRU | VACUUM 后吞吐继续下降 | 多 worker 争抢 multi-xact 缓冲区 | 随机化索引扫描起点 |
| L3 wraparound | 事务号冲到 195M | 残留 replication slot 锚定 xmin | 清理 slot + 激进 VACUUM |

SOP 改动三条：

1. **迁移演练加并发负载**。staging 里不只要跑 COPY，还要同时跑生产级别的写入。模拟真实场景才有意义。
2. **监控所有表的 bloat，不只是被迁移的表**。长事务的 blast radius 是全集群的。
3. **事故后检查 replication slot**。failover/reseed 操作后残留的 slot 是定时炸弹，`backend_xmin` 能锚住 vacuum 很久。

最后，这张图概括了三级连锁反应：

```
COPY 持 snapshot (长事务)
  │
  ├─► L1: autovacuum 无法清理 dead tuple
  │     → job queue 表 bloat → index scan 变慢 → 延迟 ↑ → 积压 ↑
  │
  ├─► L2: 多 worker 抢同一段索引
  │     → multi-xact SLRU 争用 → lightweight lock waits
  │
  └─► L3: 事务号增长 + 残留 slot 锚定 xmin
        → wraparound 逼近 → 触发 freeze vacuum
```

这种事 staging 测不出来不丢人。丢人的是不改 SOP 下次再炸一次。
