## 正常断连 vs 异常断连  vs 失联

- 正常断连的含义是tcp会发出4次挥手，两端都正常关闭连接，发FIN包
- 异常断连的含义是没有tcp 4次挥手，但tcp内核会RESET关闭连接，发RST包
- 失联的含义是RST包都没有机会发，网络中断无法通信，两端仍可以保持连接（保持各自的socket）

## TCP的FIN和RST包

FIN和RST都有正常情况和异常情况发的，总结几个要点：

1. 程序abort发的是FIN包，这包括KILL -9（已验证PG进程kill -9发FIN包）
2. 端口不可达是RST包
3. TCP keepalive超时也是RST包
4. 防火墙也有可能做RESET
5. RST包跟业务层 `connection reset by peer` 报错相关

下面是 TCP 6个控制位和 FIN/RST 的详细说明：

[TCP 6个control bits](https://linuxvox.com/blog/what-is-the-reason-and-how-to-avoid-the-fin-ack-rst-and-rst-ack/):

| Flag | Name        | Purpose                                                      |
| ---- | ----------- | ------------------------------------------------------------ |
| SYN  | Synchronize | Initiates a connection (used in the handshake).              |
| ACK  | Acknowledge | Confirms receipt of a packet (includes an ACK number for sequence tracking). |
| FIN  | Finish      | Signals intent to close a connection gracefully.             |
| RST  | Reset       | Abruptly terminates a connection (no graceful closure).      |
| PSH  | Push        | Forces immediate delivery of data (bypasses buffering).      |
| URG  | Urgent      | Marks data as "urgent" (rarely used today).                  |

FIN和RST包的区别:

**FIN Normal Causes**

`[FIN, ACK]` is part of the graceful termination process. Here’s how it typically flows:

1. Host A (e.g., a client) finishes sending data and sends a `FIN` flag to Host B (server), indicating “I’m done sending.”
2. Host B acknowledges Host A’s `FIN` with an `ACK` (so the packet is `ACK` only).
3. Host B then sends its own `FIN` (along with an `ACK` for Host A’s `FIN`), resulting in a `[FIN, ACK]` packet.
4. Host A acknowledges Host B’s `FIN` with an `ACK`, and the connection closes.

Example: When you close a browser tab, the client sends `FIN` to the web server, which responds with `[FIN, ACK]` to close its side.

**FIN Abnormal Causes**

- Premature Closure: An application crashes but still sends `FIN` (e.g., due to poor error handling).
- Linger Timeouts: If an application sets `SO_LINGER` with a short timeout (e.g., `setsockopt(SO_LINGER, 1, 0)`), the OS may send `FIN` immediately, even if data is unsent.
- Network Congestion: Delayed `ACK`s can cause `FIN` and `ACK` to be merged into `[FIN, ACK]` unexpectedly.

**Deep Dive: [RST]**

The `RST` (Reset) flag aborts a connection *immediately*—no graceful closure, no waiting for acknowledgments. It’s TCP’s “emergency stop.”

**RST Normal Causes**

- Port Unreachable: No service is listening on the target port (e.g., sending traffic to `8080` when the server only runs on `80`).
- Invalid Sequence/Ack Numbers: A packet arrives with a sequence number outside the expected window (common in misconfigured NATs).
- Connection Timeout: The OS terminates idle connections after `tcp_keepalive_time` (Linux default: 7200 seconds).
- Explicit Application Request: Apps can force `RST` via `SO_LINGER` with `linger_time=0` (e.g., `setsockopt(SO_LINGER, 1, 0)`).

**RST Abnormal Causes**

- Firewall/IPS Interference: Firewalls may drop packets, causing the receiver to send `RST` (e.g., Palo Alto Networks’ “drop” action vs. “reset”).
- Kernel Bugs: Rare, but OS kernel flaws (e.g., Linux CVE-2019-11477) can trigger spurious `RST`s.
- Resource Exhaustion: Too many open connections (e.g., `ulimit` hit) force the OS to reset new connections.
- Malicious Attacks: TCP RST attacks spoof `RST` packets to disrupt connections (e.g., targeting VoIP or VPN links).



另外要注意：

**socket.close() != 连接池close()**。一个是tcp正常断连做四次挥手，连接完全断开；一个是应用请求结束后将连接归还给连接池，连接还是保持的，此时的连接状态应是idle。

## 测试：PG进程终止、正常关库、暴力关库，客户端收到什么包

测试环境：Rocky 10.1 + PG 18.2，tcpdump 抓 lo 口 TCP 包。

| 场景 | 服务端发的包 | 四次挥手 | 客户端报错 |
|------|-------------|---------|-----------|
| `pg_terminate_backend(PID)` | `[F.]` FIN+ACK | ✅ 完整 | `FATAL: terminating connection due to administrator command` |
| `pg_ctl stop -m fast` | `[F.]` FIN+ACK | ✅ 完整 | `FATAL: terminating connection due to administrator command` |
| `kill -9 postmaster` | `[F.]` FIN+ACK | ✅ 完整 | `server closed the connection unexpectedly` |

**结论：kill -9 也发 FIN，不是 RST。** Linux TCP 内核在进程被 SIGKILL 时替进程关闭 socket，发 FIN 完成四次挥手。三种方式的客户端都收到正常的 FIN 关闭，没有任何场景发 RST。

## 测试：怎么产生 RST 包

**端口无监听（PG 已停库）**

```text
14:01:48.492004 IP 127.0.0.1.52092 > 127.0.0.1.ircu-2: Flags [S], seq 2570941791
14:01:48.492012 IP 127.0.0.1.ircu-2 > 127.0.0.1.52092: Flags [R.], seq 0, ack 2570941792, win 0
```

客户端 SYN → 内核返回 `[R.]` RST+ACK，`win 0`。psql 报 `Connection refused`。

**iptables REJECT --reject-with tcp-reset**

```text
14:02:37.768515 IP 127.0.0.1.36436 > 127.0.0.1.ircu-2: Flags [S], seq 382980016
14:02:37.768522 IP 127.0.0.1.ircu-2 > 127.0.0.1.36436: Flags [R.], seq 0, ack 382980017, win 0
```

和端口无监听完全一致：`[R.]` RST+ACK。psql 同样报 `Connection refused`。

**iptables DROP（模拟防火墙静默丢包）**

```text
14:00:07.050040 IP 127.0.0.1.33166 > 127.0.0.1.ircu-2: Flags [S], seq 985608804
14:00:08.095618 IP 127.0.0.1.33166 > 127.0.0.1.ircu-2: Flags [S], seq 985608804   ← 1s后重传
14:00:09.119647 IP 127.0.0.1.33166 > 127.0.0.1.ircu-2: Flags [S], seq 985608804   ← 2s后重传
```

服务端无任何回应，客户端 SYN 重传 3 次（1s、2s、4s 间隔）后超时。**与 REJECT 不同，DROP 不会有 RST，客户端只能靠超时感知。**

**RST 产生场景总结**

| 场景 | 协议层 | 包类型 | 触发方 |
|------|--------|--------|--------|
| 端口无监听 | TCP 内核 | `[R.]` RST+ACK | OS 内核 |
| 防火墙 REJECT | iptables | `[R.]` RST+ACK | 防火墙 |
| TCP keepalive 超时 | TCP 内核 | `[R]` RST | OS 内核（keepalive 探测失败后） |
| 进程终止 (kill -9) | TCP 内核 | `[F.]` FIN+ACK（不是 RST！）| OS 内核替进程关 socket |
| 防火墙 DROP | — | 无 | — |

**核心区分：FIN 是进程退出（内核替进程优雅关闭，哪怕是kill -9），RST 是网络不可达。**

# 如何探活

客户端的死连接问题，只能通过客户端去解决，因为服务（数据库）已经按预期访问不到了。

一个死连接放在那里，谁也不去动他当然会存在，这里就需要探活。我自己总结了一下常见的探活机制按网络类型分为两种：

| 网络         | 动作        | 参数                                                         | 发送的内容                                                   |
| ------------ | ----------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 4层探活      | 内核层tcp包 | linux内核参数`tcp_keepalive`,`tcp_retries2`；连接池支持的    | `tcp_keepalive`发送的是ACK，`tcp_retries2`发的什么？         |
| 7层探活      | 数据库命令  | testOnBorrow类：`testOnBorrow` ,`testOnReturn`,`TestWhileIdle` ；PING类：`Ping`等连接池所支持的参数 | 视驱动而定，可配置命令，例如`SELECT NOW()`,`SELECT 'x'`;`PING` |
| 7层探活-主从 | 数据库命令  |                                                              | x需要配置test-query，例如`SELECT @@READ_ONLY`;`SELECT NOT pg_is_in_recovery()`; |
